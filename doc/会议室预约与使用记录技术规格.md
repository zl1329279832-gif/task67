## 2. sfsh 审核状态详解

### 2.1 状态枚举与流转

`sfsh` 字段("是否审核"的拼音缩写)是预约记录的核心状态标记，取值如下:

| 值 | 含义 | 设置时机 |
|----|------|---------|
| `"待审核"` | 等待管理员审批 | `/save` 或 `/add` 创建预约时自动设置 |
| `"通过"` | 审批通过 | 管理员调用 `/shenhe` 接口 |
| `"驳回"` | 审批驳回 | 管理员调用 `/shenhe` 接口 |

**状态机规则** (源自 `HuiyishiyuyueController.shenhe()`, 第 214-265 行):

```
待审核 ──┬── 通过 (终态，同时自动创建使用记录)
         └── 驳回 (终态)
```

- 仅 `"待审核"` 状态可触发审核，已审核记录不可重复操作
- 不存在"驳回后重新提交"机制 -- 被驳回的预约需新建
- 不存在"通过后取消"机制 -- 通过即最终

### 2.2 前后端不一致问题

**后端** (`HuiyishiyuyueController`): 使用三态值 `"待审核" / "通过" / "驳回"`

**管理后台 Vue 前端** (`huiyishiyuyue/list.vue`): 部分代码仍使用旧的二态逻辑:
```javascript
// list.vue 约第 510 行
sfshOptions = "是,否".split(',')

// list.vue 约第 211 行
scope.row.sfsh=='是' ? '通过' : '未通过'
```

这导致管理界面的审核筛选下拉框与后端实际值不匹配。管理员通过旧前端界面的通用审核按钮操作可能写入 `"是"` 而非 `"通过"`，造成数据不一致。

### 2.3 通用审核接口的隐患

`CommonController` (路径 `POST /sh/{tableName}`) 提供了一个**绕过业务逻辑的通用审核入口**:

```sql
UPDATE ${table} SET sfsh=#{sfsh} WHERE id=#{id}
```

该接口:
- 不校验 `sfsh` 的合法取值
- 不检查当前状态是否为 `"待审核"`
- 不触发使用记录的自动创建
- 存在 SQL 注入风险 (tableName 来自 URL 路径)

如果前端调用 `/sh/huiyishiyuyue` 而非 `/huiyishiyuyue/shenhe`，会导致审核通过但不生成使用记录。

## 3. 预约流程分析

### 3.1 创建预约 (POST /huiyishiyuyue/save 或 /add)

```
请求体 (JSON):
{
  "yuyuebianhao": "YY202604001",
  "huiyishibianhao": "H001",
  "huiyishimingcheng": "第一会议室",
  "huiyishiguimo": "大型",
  "huiyishiweizhi": "3楼301",
  "yujirenshu": "20",
  "kaishishijian": "2026-06-15 09:00:00",
  "jieshushijian": "2026-06-15 11:00:00",
  "huiyishuoming": "项目评审会",
  "yonghuzhanghao": "zhangsan",
  "yonghuxingming": "张三",
  "shoujihaoma": "13800138000",
  "bumen": "技术部",
  "shebeibianhao": "SB001,SB003"
}
```

**后端处理步骤** (`HuiyishiyuyueController.save()`, 第 136-159 行):

1. 生成 ID: `new Date().getTime() + random(0~999)`
2. 设置 `sfsh = "待审核"` (若前端未传)
3. 设置 `shenqingshijian = new Date()`
4. 校验部门归属 (仅 `yonghu` 角色): 确认提交的部门与用户自身部门一致
5. **校验会议室时间冲突** (`checkTimeConflict`):
   - 查询同一 `huiyishibianhao`、`sfsh IN ("待审核","通过")` 的记录
   - 判断时间重叠: `已有.jieshushijian > 新.kaishishijian AND 已有.kaishishijian < 新.jieshushijian`
   - 冲突则抛出 `EIException` 终止
6. **校验设备时间冲突** (`checkEquipmentConflict`):
   - 查询同时间段内 `sfsh IN ("待审核","通过")` 的所有预约
   - 将 `shebeibianhao` 按逗号拆分，逐一比较是否有交集
   - 任一设备被占用则抛出 `EIException` 终止
7. 插入数据库

### 3.2 修改预约 (POST /huiyishiyuyue/update)

**后端处理步骤** (`HuiyishiyuyueController.update()`, 第 196-208 行):

1. 仅在 `kaishishijian` 和 `jieshushijian` **同时不为 null** 时重新校验冲突
2. 使用 `excludeId` 排除自身记录
3. 调用 `updateById()` 全字段更新

**已知问题**:
- 不检查当前 `sfsh` 状态 -- 已通过/已驳回的预约也可被修改
- 不校验部门归属
- 若只修改 `kaishishijian` 而不传 `jieshushijian` (或反之)，冲突检测被跳过

### 3.3 审核预约 (POST /huiyishiyuyue/shenhe)

```
请求体 (JSON):
{
  "id": 1718438400123,
  "sfsh": "通过",
  "shhf": "同意使用"
}
```

**后端处理步骤** (`HuiyishiyuyueController.shenhe()`, 第 214-265 行):

1. 校验 `id` 非空
2. 校验 `sfsh` 取值仅限 `"通过"` 或 `"驳回"`
3. 查询原记录，确认存在
4. 确认原状态为 `"待审核"` (否则拒绝重复审核)
5. 若 `sfsh = "通过"`:
   - 创建 `ShiyongjiluEntity`
   - 复制会议室编号、名称、规模、位置
   - 设置 `shiyongshijian = 原记录.kaishishijian`
   - 拼接 `beizhu` = `"预约编号:XXX,使用人:XXX,时段:XXX-XXX"`
   - 插入 `shiyongjilu` 表
6. 更新原记录的 `sfsh` 和 `shhf`

## 4. Shiyongjilu 与预约的断裂点分析

### 4.1 当前关联方式

使用记录 (`shiyongjilu`) 与预约 (`huiyishiyuyue`) 之间**没有外键或 ID 引用关系**。两者的关联仅依赖:
- 数据复制: 会议室编号/名称等字段从预约记录逐一复制到使用记录
- `beizhu` 文本拼接: 将预约编号、使用人、时段以纯文本形式写入备注字段

### 4.2 断裂点清单

| 编号 | 断裂点 | 影响 |
|------|--------|------|
| D-1 | **无预约 ID 外键**: `shiyongjilu` 表没有 `yuyue_id` 字段 | 无法从使用记录反查原始预约，无法做数据关联统计 |
| D-2 | **使用记录仅保留开始时间**: `shiyongshijian` 取自 `kaishishijian`，无结束时间 | 无法判断使用时长，无法做会议室利用率分析 |
| D-3 | **不记录使用人信息**: `shiyongjilu` 无 `yonghuzhanghao`/`yonghuxingming` 字段 | 使用人信息被埋在 `beizhu` 文本中，无法结构化查询 |
| D-4 | **不记录设备信息**: `shiyongjilu` 无 `shebeibianhao` 字段 | 无法追踪设备的实际使用情况 |
| D-5 | **容纳人数来源错误**: 取 `huiyishi.rongnarenshu` 而非 `huiyishiyuyue.yujirenshu` | 但当前 `shenhe()` 实际上并未填充 `rongnarenshu`，该字段始终为 null |
| D-6 | **独立 CRUD 可直接操作**: `ShiyongjiluController` 提供完整增删改查 | 管理员可手动创建/删除使用记录，绕过预约流程 |
| D-7 | **预约修改不同步使用记录**: `update` 不检查是否已生成使用记录 | 审核通过后修改时间，使用记录中的信息变为过期 |
| D-8 | **删除预约不级联**: `delete` 不检查关联使用记录 | 预约被删除后使用记录成为孤儿数据 |

## 6. 并发冲突场景说明

当前的 `checkTimeConflict()` 方法使用 **先查后插** 模式:

```java
// HuiyishiyuyueServiceImpl.java 第 66-83 行
int count = this.selectCount(ew);  // 步骤1: 查询是否冲突
if (count > 0) {
    throw new EIException("...");  // 步骤2: 有冲突则抛异常
}
// HuiyishiyuyueController.java 第 158 行
huiyishiyuyueService.insert(huiyishiyuyue);  // 步骤3: 无冲突则插入
```

**竞态窗口**: 步骤 1 和步骤 3 之间没有数据库级锁。两个并发请求可同时通过步骤 1 的检查，然后都执行步骤 3 的插入，形成 double booking。

**触发条件**: 两位用户在短时间内(毫秒级)为同一会议室的同一时段提交预约。在高峰时段(如周一上午抢订会议室)概率显著升高。
