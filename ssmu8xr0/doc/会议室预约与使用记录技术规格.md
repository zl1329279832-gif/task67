## 2. 预约流程：create / update 详解

### 2.1 创建预约

**入口**:
- 后台管理端: `POST /ssmu8xr0/huiyishiyuyue/save`
- 前台用户端: `POST /ssmu8xr0/huiyishiyuyue/add`

两个入口共享相同的业务逻辑（`HuiyishiyuyueServiceImpl`），执行顺序如下：

```
┌─────────────────────────────────────────────────────┐
│  Step 1: 自动字段填充                                 │
│  ├─ sfsh ← "待审核"                                  │
│  └─ shenqingshijian ← new Date()                     │
├─────────────────────────────────────────────────────┤
│  Step 2: 部门校验 (仅 yonghu 角色)                    │
│  └─ validateDepartment(entity, sessionUser.bumen)     │
│     → 不匹配则抛出 "只能预约本部门的会议室"              │
├─────────────────────────────────────────────────────┤
│  Step 3: 会议室时间冲突校验                            │
│  └─ checkTimeConflict(entity, null)                   │
│     → SQL: WHERE huiyishibianhao = ?                 │
│              AND sfsh IN ('待审核','通过')              │
│              AND jieshushijian > newStart              │
│              AND kaishishijian < newEnd                │
│              [AND id != excludeId]                     │
│     → 存在重叠则抛出 "该时间段已被预约"                 │
├─────────────────────────────────────────────────────┤
│  Step 4: 设备时间冲突校验                              │
│  └─ checkEquipmentConflict(entity, null)              │
│     → 解析 shebeibianhao (逗号分隔)                    │
│     → 查找同时段所有预约的设备编号                      │
│     → 交集非空则抛出 "设备 XX 在该时段已被预约"          │
├─────────────────────────────────────────────────────┤
│  Step 5: 持久化                                       │
│  └─ service.insert(entity)                            │
└─────────────────────────────────────────────────────┘
```

### 2.2 修改预约

**入口**: `POST /ssmu8xr0/huiyishiyuyue/update`

```
┌─────────────────────────────────────────────────────┐
│  Step 1: 加载原始记录                                 │
│  └─ oldEntity = service.getById(id)                  │
├─────────────────────────────────────────────────────┤
│  Step 2: 条件性冲突校验                               │
│  ├─ IF 时间或会议室变更 → checkTimeConflict(new, id)  │
│  └─ IF 时间或设备变更   → checkEquipmentConflict(new, id)│
│  （excludeId = 当前记录 id，避免自我冲突）              │
├─────────────────────────────────────────────────────┤
│  Step 3: 更新                                         │
│  └─ service.updateById(entity)                        │
└─────────────────────────────────────────────────────┘
```

**⚠ 注意**: 修改预约时 **不重新校验部门**，即管理员可将 A 部门预约改为 B 部门会议室，绕过部门隔离。

### 2.3 删除预约

**入口**: `POST /ssmu8xr0/huiyishiyuyue/delete`（批量，接收 `Long[] ids`）

- 无业务校验，直接物理删除
- **不会级联删除** 对应的 `shiyongjilu` 使用记录
- 已审核通过的预约被删除后，使用记录成为孤儿数据

## 3. `sfsh` 审核状态语义

### 3.1 状态定义

| 状态值 | 含义 | 设置时机 |
|---|---|---|
| `"待审核"` | 已提交，等待管理员审核 | 创建预约时自动设置（硬编码） |
| `"通过"` | 审核通过，预约生效 | 管理员调用审核接口 |
| `"驳回"` | 审核拒绝，预约无效 | 管理员调用审核接口 |

### 3.2 审核接口

**入口**: `POST /ssmu8xr0/huiyishiyuyue/shenhe`

**请求体** (JSON):
```json
{
  "id": 1234567890,
  "sfsh": "通过",
  "shhf": "同意使用三楼大会议室"
}
```

**业务逻辑**:

```
┌───────────────────────────────────────────────────────────┐
│  Step 1: 加载预约记录                                     │
│  └─ entity = service.getById(id)                          │
├───────────────────────────────────────────────────────────┤
│  Step 2: 状态校验                                          │
│  └─ sfsh 必须为 "通过" 或 "驳回"，否则抛异常               │
├───────────────────────────────────────────────────────────┤
│  Step 3: 更新审核字段                                      │
│  ├─ entity.sfsh = request.sfsh                            │
│  └─ entity.shhf = request.shhf                            │
├───────────────────────────────────────────────────────────┤
│  Step 4: 若通过 → 自动创建使用记录                          │
│  ├─ new ShiyongjiluEntity()                               │
│  ├─ 复制: huiyishibianhao, huiyishimingcheng,             │
│  │        huiyishiguimo, huiyishiweizhi                    │
│  ├─ rongnarenshu ← yujirenshu (预计人数 → 容纳人数)        │
│  ├─ shiyongshijian ← kaishishijian (开始时间)              │
│  ├─ beizhu ← "预约编号:{yuyuebianhao},                    │
│  │          申请人:{yonghuxingming},                        │
│  │          时间:{kaishishijian}~{jieshushijian}"           │
│  └─ shiyongjiluService.insert(record)                     │
├───────────────────────────────────────────────────────────┤
│  Step 5: 更新预约记录                                      │
│  └─ service.updateById(entity)                            │
└───────────────────────────────────────────────────────────┘
```

### 3.3 审核状态在冲突校验中的角色

冲突校验 SQL 的 `WHERE sfsh IN ('待审核', '通过')` 意味着：
- **`驳回` 的预约不占用时段** — 被驳回后，该时段自动释放
- **`待审核` 的预约也占用时段** — 这导致一种边界情况：用户 A 提交预约后（待审核），用户 B 无法预约同一时段；即使 A 最终被驳回，B 在 A 审核前也无法提交

## 4. Shiyongjilu（使用记录）与预约的断裂点分析

### 4.1 当前关联方式

使用记录 **仅在审核通过时自动创建一条**，关联完全依赖冗余字符串字段，无外键约束：

```
huiyishiyuyue.yuyuebianhao ──(写入 beizhu 文本)──→ shiyongjilu.beizhu
huiyishiyuyue.huiyishibianhao ──(字符串复制)──→ shiyongjilu.huiyishibianhao
```

**不存在** `yuyue_id` 或任何外键字段将使用记录反向关联到预约。

### 4.2 断裂点清单

| # | 断裂点 | 现状 | 影响 |
|---|---|---|---|
| **4.2.1** | 无外键关联 | `shiyongjilu` 没有 `yuyue_id` 字段 | 无法从使用记录反查预约；beizhu 中的预约编号是纯文本，不可 JOIN |
| **4.2.2** | 时间语义丢失 | 使用记录仅有 `shiyongshijian`（单一时间点），取 `kaishishijian` | 结束时间 `jieshushijian` 丢失，无法还原预约时段 |
| **4.2.3** | 仅审核通过时创建 | 只在 `/shenhe` 且 `sfsh="通过"` 时插入 | 手动创建的使用记录（`/shiyongjilu/save`）与预约完全脱钩 |
| **4.2.4** | 前端审核路径不一致 | 后台 list.vue 的审核弹窗调用的是 `huiyishiyuyue/update`（通用更新），**而非** `/shenhe` | 通过前端审核时 **不会自动创建使用记录**，只有直接调用 `/shenhe` 才会 |
| **4.2.5** | 设备信息不传递 | 使用记录无 `shebeibianhao` 字段 | 审核通过后的使用记录丢失了设备预约信息 |
| **4.2.6** | 无签到/签退机制 | 使用记录在审核时就创建，而非实际使用时 | 无法区分"预约了但没用"和"实际使用了"，统计数据失真 |
| **4.2.7** | 删除不级联 | 删除预约不会删除对应使用记录 | 预约被删后使用记录成为孤儿数据 |
| **4.2.8** | 前端审核状态值不一致 | `/shenhe` 接口接受 `"通过"/"驳回"`，但前端审核弹窗选项是 `"通过"/"不通过"` | 若前端弹窗选了"不通过"发送到 `/shenhe`，会被 Step 2 校验拒绝 |
| **4.2.9** | 容纳人数语义混淆 | 预约表 `yujirenshu`（预计人数）→ 使用记录 `rongnarenshu`（容纳人数） | 语义错位：预计 10 人开会，记录里变成"容纳 10 人" |

### 4.3 前端审核路径详解（断裂点 4.2.4）

**后台管理端 `list.vue`** 的审核对话框：

```javascript
// list.vue 审核提交逻辑
this.$http({
  url: `huiyishiyuyue/update`,    // ← 通用 update，不是 /shenhe
  method: "POST",
  data: {
    id: this.shForm.id,
    sfsh: this.shForm.sfsh,       // "通过" 或 "不通过"
    shhf: this.shForm.shhf
  }
})
```

而 `/update` 接口的行为是：
1. 检查时间变更 → 有变更才重新校验冲突
2. 直接 `updateById(entity)` — **不触发使用记录创建**

这意味着：**当前后台管理界面审核通过预约时，使用记录根本不会被自动创建。** `/shenhe` 接口虽然实现了自动创建逻辑，但前端并未使用它。

## 6. 冲突校验机制详解

### 6.1 会议室时间冲突 (`checkTimeConflict`)

```sql
-- 等效 SQL（MyBatis-Plus Wrapper 生成的查询）
SELECT COUNT(*) FROM huiyishiyuyue
WHERE huiyishibianhao = #{entity.huiyishibianhao}
  AND sfsh IN ('待审核', '通过')
  AND jieshushijian > #{entity.kaishishijian}
  AND kaishishijian < #{entity.jieshushijian}
  AND id != #{excludeId}   -- 修改时排除自身
```

**重叠判断逻辑**：两个时段 `[A_start, A_end)` 和 `[B_start, B_end)` 重叠当且仅当 `A_end > B_start AND A_start < B_end`。

**边界情况**:
- 精确相邻（前一个结束时间 = 后一个开始时间）**不算冲突** — 这是正确的
- 完全包含（新预约在某预约内部）**算冲突** — 正确
- `sfsh = '驳回'` 的预约**不参与冲突计算** — 驳回后时段自动释放

### 6.2 设备时间冲突 (`checkEquipmentConflict`)

```
1. 解析当前预约的 shebeibianhao → Set<String> currentEquipIds
2. 查找同时段所有有效预约（sfsh IN 待审核,通过，排除自身）
3. 对每条重叠预约，解析其 shebeibianhao → Set<String> overlapEquipIds
4. 求交集: currentEquipIds ∩ overlapEquipIds
5. 交集非空 → 抛出异常，列出冲突设备编号
```

**⚠ 潜在问题**: `shebeibianhao` 存储为逗号分隔字符串（如 `"1,3,7"`），冲突检测通过 Java 内存计算而非 SQL JOIN，在预约量大时性能堪忧。且 Mapper XML 的 `resultMap` 未包含 `shebeibianhao`，自定义查询路径无法获取该字段。

## 附录 A: 关联 Controller 与预约的潜在关联及未实现项

### A.1 HuiyishiController (`/huiyishi`)

| 已实现 | 说明 |
|---|---|
| 标准 CRUD | `/page`, `/list`, `/save`, `/update`, `/delete` 等 |
| `keyueshijian` 字段 | 会议室表有"可约时间"字段（String 类型，人工填写） |

| 未实现 | 影响 |
|---|---|
| **预约时不查询会议室可用性** | `/huiyishiyuyue/save` 不校验 `huiyishi.keyueshijian`，仅检查已有预约的时间冲突。管理员设置的可约时间形同虚设 |
| **不校验容纳人数** | 预约的 `yujirenshu` 可以超过会议室的 `rongnarenshu`，无告警 |
| **冗余字段不同步** | 修改会议室名称/位置后，已有预约中的冗余字段不更新 |
| **无状态管理** | 会议室无"停用/维护"状态，无法阻止对不可用会议室的预约 |
| **无预约统计视图** | 无法按会议室查看预约频率、利用率 |

### A.2 ShebeixinxiController (`/shebeixinxi`)

| 已实现 | 说明 |
|---|---|
| 标准 CRUD | 设备信息的增删改查 |
| 设备编号 | 可作为预约表 `shebeibianhao` 的引用值 |

| 未实现 | 影响 |
|---|---|
| **无引用完整性校验** | 预约时可填入不存在的设备编号，系统不校验 |
| **无设备状态管理** | 设备无"在用/维修/报废"状态，损坏设备仍可被预约 |
| **设备数量不扣减** | `shebeixinxi.shuliang`（数量）在预约时不检查也不扣减，同一设备可被无限预约 |
| **设备与会议室无绑定** | `shebeixinxi.shebeiweizhi` 是文本字段，不关联 `huiyishibianhao`，无法查询某会议室有哪些设备 |
| **设备预约历史不可查** | 无法按设备查看预约时间线 |

### A.3 BumenController (`/bumen`)

| 已实现 | 说明 |
|---|---|
| 标准 CRUD | 部门名称的增删改查 |

| 未实现 | 影响 |
|---|---|
| **部门名称无唯一约束** | 可创建重名部门，预约时部门校验可能匹配到错误部门 |
| **无层级结构** | 不支持"行政部-后勤组"这样的子部门预约隔离 |
| **部门与会议室无绑定** | 会议室表无 `bumen` 字段（仅通过位置间接区分），部门校验逻辑依赖预约时用户选择的会议室是否属于本部门，但判断依据仅为字符串比较 |
| **部门变更不追溯** | 用户调岗后，历史预约的 `bumen` 字段不更新 |

### A.4 跨 Controller 未实现的协同功能

| 预约 → 签到闭环 | Huiyishiyuyue + Shiyongjilu | 使用记录在审核时创建而非签到时，无实际使用追踪 |
